# tkt — Design

`tkt` is a multi-project ticket manager for agent-driven development. It lists the current sprint's tickets across several Jira projects, starts work on a ticket (opens an agent that creates the branch and worktree per project rules), and shows the status of every ticket, including its pull requests and CI, on one board.

Status: design. Phase 1 (CLI) has not started. Sections marked **Draft** are refined when their phase begins.

## 1. Goals and non-goals

Goals:

- One view of "my sprint" across Jira projects (DEMO, OPS, and others), joined with GitHub pull requests and CI.
- Start a ticket in one step: open an agent (Claude Code, OpenCode, or any other Herdr can start) in Herdr that creates the branch and worktree per project rules and registers them with `tkt`.
- A deterministic core that works without any LLM.
- Runs on macOS, Linux, and Windows through WSL2.

Out of scope: voice, system control, own memory, multi-user. No early generalization: the user's projects live in configuration, not in a generic plugin system.

## 2. Architecture

```
┌──────────────┐ ┌─────────────┐ ┌──────────────┐ ┌────────────────────┐
│ Herdr plugin │ │ Web UI      │ │ Tray app     │ │ Claude Code        │
│ (calls CLI)  │ │ (browser)   │ │ (same UI)    │ │ skill → MCP        │
└──────┬───────┘ └──────┬──────┘ └──────┬───────┘ └─────────┬──────────┘
       │ exec           └───── HTTP + WebSocket ─────┐       │ exec / stdio
       ▼                                             ▼       ▼
┌──────────────────────────────────────────────────────────────────────┐
│ tkt (single Go binary)                                               │
│  CLI/TUI · daemon (SQLite cache, background sync, API v1) · MCP     │
└───────────────┬───────────────────────────────┬──────────────────────┘
                ▼                               ▼
            Jira Cloud                     GitHub (PRs, CI)
```

Rules:

- `tkt` is the only component that talks to Jira and GitHub. Every other component is a thin client.
- One binary, three roles: `tkt <command>` (CLI/TUI), `tkt daemon` (cache, sync, local API, embedded UI), `tkt mcp` (MCP server over stdio).
- When the daemon is running, the CLI and MCP read through it; when it is not, the CLI works directly against Jira and GitHub (phase 1 has no daemon).

### Proposed code layout

```
cmd/tkt/             entrypoint, command wiring
internal/ticket/     domain: ticket, sprint, status, branch-name convention (no I/O)
internal/jira/       Jira adapter (REST, ADF → Markdown)
internal/github/     GitHub adapter (PRs, checks)
internal/workspace/  worktree discovery, links, agent launch (never creates branches)
internal/config/     ~/.config/tkt loading and validation
internal/secrets/    keychain / credential store
internal/daemon/     cache, sync loop, API v1, event hub   (phase 3)
internal/mcp/        MCP server                           (phase 4)
web/                 React + Vite UI, embedded with go:embed (phase 3)
plugin/herdr/        Herdr plugin manifest and scripts    (phase 2)
```

Domain code depends on nothing; adapters implement ports defined next to the use cases that need them.

## 3. Daemon API v1 (Draft — the most important contract)

Designed now, implemented in phase 3. Every client depends on it, so it is versioned from the first commit.

Transport and auth:

- Listens on `127.0.0.1` only (never `0.0.0.0`). Default port configurable; the chosen port is written next to the token.
- A random 256-bit token is generated at first start and stored in `<data>/token` with mode `0600`.
- HTTP requests send `Authorization: Bearer <token>`. `GET /health` is the only unauthenticated route and reveals nothing beyond liveness and version.
- WebSocket at `/v1/ws`. Browsers cannot set headers on a WebSocket upgrade, so the first client message must be `{"type":"hello","token":"…","protocol":1}`; otherwise the socket closes with code `4401` (pattern taken from gentle-dot). The upgrade also checks `Origin` against an allowlist (the daemon's own origin and the tray shell's origin).

Versioning:

- HTTP routes are prefixed with `/v1`. Breaking changes create `/v2`; additive changes (new fields, new event types) do not.
- Clients must ignore unknown fields and unknown event types.

Resources (Draft):

| Method | Route | Purpose |
|---|---|---|
| GET | `/health` | liveness, version, protocol |
| GET | `/v1/tickets` | sprint tickets across projects, with PR and CI summary |
| GET | `/v1/tickets/{key}` | one ticket with description, comments, PRs, checks; why it needs the user, its agent, its work |
| GET | `/v1/tickets/{key}/context` | the Markdown the board's "copy context" puts on the clipboard |
| GET | `/v1/board` | the Sprint screen as the board lays it out: columns, list sections, Boards filter, sync state |
| GET | `/v1/board/state` | what the board remembers between openings (`board-state.json`) |

| GET | `/v1/prs` | the PRs tab as the board lays it out: the user's pull requests, review requests, Repos filter |
| GET | `/v1/backlog` | the Backlog as the board lays it out: sprints and sprintless tickets, Split or Merged, Boards filter |
| GET | `/v1/tickets/{key}/start` | what the board's Start modal asks: worktrees, repositories, agents |
| POST | `/v1/tickets/{key}/start` | open the agent in the selected repositories (via Herdr) |
| GET | `/v1/tickets/{key}/transitions` | where the board's Move menu can move a ticket, with each move's form |

| GET | `/v1/tasks/agents` | the agents open in Herdr that a ticket's feedback or a review can go to, and the kinds of a new agent |
| POST | `/v1/tasks` | send a ticket's feedback or a review to its own agent, an open agent, or a new one (via Herdr) |
| GET | `/v1/settings` | the TUI's Settings: spaces and repositories, team boards, local clones, board fields, and the columns and marks a status can take |
| PATCH | `/v1/settings` | change what Settings changes, saved to `config.toml` |
| GET | `/v1/settings/statuses`, `/v1/settings/boards`, `/v1/settings/fields` | what Settings lists from Jira: a space's statuses with their column and mark, its scrum boards, the site's fields |
| POST | `/v1/tickets/{key}/links` | register a branch and worktree created by the agent (not served yet; `tkt link` writes them) |
| POST | `/v1/sync` | request an immediate sync |
| POST | `/v1/confirmations/{id}` | user accepts or rejects a pending write (not served yet; clients confirm in their own UI) |

Events over WebSocket:

- Envelope: `{"seq": <n>, "type": "<event>", "ts": "<RFC 3339>", "data": {…}}`.
- `seq` starts at 1 per connection and increases by exactly 1. A client that sees a jump knows it missed events, discards its cached state, and refetches with `GET /v1/tickets` (or reconnects).
- After `hello`, the daemon sends `snapshot` with the full current state; events after that are deltas.
- Initial event types: `snapshot`, `ticket.updated`, `ticket.removed`, `link.added`, `pr.updated`, `checks.updated`, `agent.updated`, `sync.started`, `sync.finished`, `sync.failed`, `auth.expired`, `confirmation.requested`, `confirmation.resolved`; the Herdr desktop mod's API adds `start.finished`, `start.failed`, `task.finished`, `task.failed`, `state.updated` and `settings.updated`.
- `agent.updated` carries the agent state of each linked worktree (working, blocked, idle, none) and since when. The daemon reads it from Herdr's socket API (`pane.agent_status_changed` events); without Herdr the state is `none`.
- Errors: `{"type":"error","code":"<machine code>","message":"…"}`.

### Phase 3a: the daemon for the Herdr plugin

Phase 3a builds the part of this contract the Herdr plugin, the board and `tkt list` need; the rest follows with the web UI.

- Routes: `GET /health`, `GET /v1/tickets` (the board snapshot), `GET /v1/tickets/{key}` (one ticket with description, comments and pull requests, loaded with the daemon's Jira token so `tkt show` and the Herdr ticket pane skip reading the credential store), `POST /v1/sync`, and `/v1/ws`. Events: `snapshot`, `ticket.updated`, `ticket.removed`, `agent.updated`, `sync.started`, `sync.finished`, `sync.failed`. A sync that changes more than tickets (reviews, sprints, repositories, warnings) sends a new `snapshot` instead of deltas. While a sync waits for GitHub, the daemon serves the board as Jira tells it (`"partial": true`, each ticket with its earlier pull requests) from `GET /v1/tickets` and announces it with a `snapshot` event; the full board replaces it when the sync ends, or the last full board comes back if the sync fails. A client that falls 64 events behind is dropped and reconnects. Before the first board exists, `hello` is answered by the first sync's `snapshot`.
- Team tickets: while the board's Team toggle is on (`team` in `board-state.json`, read at every sync), a sync asks each team board configured for the space (`team_boards = [{ id, name }]`, empty by default) for its active sprints, all at once, and adds one Jira search for those sprints' tickets assigned to others or to nobody (`team: true` and `board` in the snapshot); with no team board there is no search, and the team's sprints never join the board's title. Team boards are set in `tkt init` (by name, per space, only when the space has scrum boards) and in Settings, in a Team boards section of their own (one list per space; short tab names on a narrow pane), where `tab` completes a board's name from the space's scrum boards and `d` or the ✕ removes one. They skip the development panel and the search for older pull requests, take their pull requests from the repositories' listing, never need the user (no alerts), and stay out of `tkt list`'s text.
- Sync: every minute and on `POST /v1/sync`. Merged pull requests are listed with only the fields the board shows (number, title, link, state, branch, author), which halves GitHub's answer time, and the Jira client with the field ids it looked up is kept for the process. Jira and GitHub are polled, since their webhooks need a public endpoint a `127.0.0.1` daemon does not have. A ticket's development panel is asked again only when the issue's `updated` changed or the last answer is older than ten minutes.
- Herdr: the daemon subscribes to `pane.agent_status_changed` (`events.subscribe`), maps each workspace to its ticket (by the key in its folders' branch or, before an agent has made its branch, by the `tkt_key` value tkt reports on the agent's pane when it hands it a ticket, with Start or a ticket's feedback sent to it; a review marks nothing), rewrites the sidebar lines at once and sends `agent.updated`. Herdr plugins cannot keep a process alive, so the daemon lives outside the plugin.
- Start: automatic. The Herdr `[[startup]]` hook, the board and `tkt list` start `tkt daemon run` in the background when `GET /health` does not answer; a lock file in the data directory keeps one daemon per user. `tkt daemon status` and `tkt daemon stop` manage it; a launchd or systemd service can come later. A release of `tkt` replaces a running daemon of an older release or a dev build (an upgrade otherwise leaves the old code serving), and never a newer one, so an old board still open cannot fight a newer daemon. A daemon of a release asks its binary for its version every minute and, when an upgrade put a newer release in its place, starts `tkt daemon start` from it, which replaces it, so an upgrade takes over within a minute without a board or a hook. A daemon of a release, and Herdr's startup hook (`tkt herdr restore`), also bring an installed Herdr plugin up to it, so an upgrade needs no `tkt herdr install`: when the plugin's manifest names another version it is rewritten and linked again, a shortcut tkt moved (`RetiredBindings`) follows inside tkt's own block of the Herdr config, backed up first, and a shortcut the user never accepted is only announced, once, on the board's status line; when the shortcuts cannot be checked (Herdr's defaults unreadable, for one) they are retried at the next start, `herdr-synced` in the data directory recording the release that finished; a dev build or a machine without the plugin is left alone.
- Board: a refresh (`g`, or the board's own every two minutes) asks the daemon to sync and shows the spinner from `sync.started` until `sync.finished` brings the board or `sync.failed` its error; the daemon's own minute syncs show the same way. A refresh that hears nothing for 90 seconds stops spinning.
- Cache: the JSON snapshot cache the CLI already keeps, written only by the daemon while it runs; SQLite arrives with the web UI.
- Without the daemon, every client works as before, straight against Jira and GitHub.

### Herdr desktop mod: the board's layout

The Herdr desktop mod is a thin client that shows the same board as the TUI, so the daemon serves the board already laid out by the code the TUI uses (`internal/board/view.go`), never a second copy of its rules.

Rules every route of the mod's API follows:

- Auth: every `/v1` route takes `Authorization: Bearer <token>` (`401 unauthorized` otherwise); the WebSocket takes the token in its `hello`.
- Mutating routes (`POST /v1/tickets/{key}/start`, `POST /v1/tickets/{key}/transitions`, `PUT /v1/tickets/{key}/assignee`, `POST /v1/tasks`, `PATCH /v1/board/state`, `PATCH /v1/settings`) take only `Content-Type: application/json` (`415 unsupported_media_type`), a body of at most 64 KB, and no `Origin` or the daemon's own (`403 forbidden_origin`), as the WebSocket checks it.
- Errors: `{"type": "error", "code": "<machine code>", "message": "…"}`; a malformed key answers `400 bad_key`, a malformed body or query `400 bad_request`, a route this daemon was started without `404 not_found`, and a route that needs the board before the first sync `503 not_synced`.
- Boolean query parameters accept only `true` or `false`; any other value, an empty one included, answers `400 bad_request` naming the parameter.
- A request the daemon cannot settle without the user answers `409 needs_answer` with `needs` (and what the client must show to ask), before anything happens; the client asks and sends the request again with the answer.
- Work that takes long (opening agents, cloning) answers `202 {"id", "state": "started"}` and ends with an event over the WebSocket carrying that `id` (`start.finished`/`start.failed`, `task.finished`/`task.failed`); work done at once answers `200`.
- Writes to Jira or GitHub change things for everyone, so the client asks the user to confirm in its own UI before calling them, as the TUI does; the daemon never asks, and never from an agent or MCP alone.
- Contract fixtures: each endpoint the mod reads has its JSON response, for fictitious data, under `internal/daemon/testdata/contract/v1/`, compared by `go test ./internal/daemon -run Contract` and rewritten with `-update`; the mod's own tests read the same files, so a change of shape fails on both sides.

Routes:

- `GET /v1/board` is the Sprint screen. It shows the board as the user last left it (`team` and `hidden_boards` from `board-state.json`); the query `?team=true|false` and `?hidden_boards=<name>` (repeated; an empty value means none) override it for that request. It answers `503 not_synced` before the first board, as `GET /v1/tickets` does. Fields: `fetched_at`, `partial`, `syncing` (a sync is running), `sync_error` (the last sync failed, with its message; the board is the last good one), `team`, `hidden_boards`, `boards` (each team board the Boards filter offers, by name: `name`, `tickets`, `hidden`), `columns` (To Do, In Progress, In Review, Done in order: `category`, `title`, `points`, `rows`), `sections` (the list's blocks in order, such as `My tickets` then `Team · <board>` per board: `title`, `count`, `rows`), `agents` (agent state by ticket key), `label_field`, `warnings`. A row is `{key, parent, ticket}`: a ticket, or a subtask (`parent` set) placed as the TUI places it, after its parent in the list and in its own column in Columns.
- `GET /v1/prs` is the PRs tab, from the same snapshot (`503 not_synced` before the first board). It shows the tab as the user last left it (`hidden_repos`, `collapsed` and `team_prs` from `board-state.json`, `team_prs` following `team` while unset); the query `?team_prs=true|false`, `?bots=true|false` (bots are hidden unless asked, as in the TUI, which does not remember it) and `?hidden_repos=<owner/name>` (repeated; an empty value means none) override it. Fields: `fetched_at`, `partial`, `syncing`, `sync_error`, `hidden_repos`, `collapsed`, `team_prs`, `bots`, `hidden_bots` (pull requests opened by bots, which `bots=true` shows), `repos` (each repository the Repos filter offers: `name`, `prs` open, `hidden`), `sections` (in order: `Mine · <repo>` per repository, those needing the user first; then `Review requested · <repo>`, or with `team_prs` every open pull request by repository with the review requests among them: `group`, `title`, `count`, `needs`, `collapsed`, `rows`), `warnings`. A row is `{key "#N", pr, ticket, other, review, status, approvals, needs_you}`; `status` is the STATUS the TUI shows, such as `CI failing` or `Review requested`. Sections carry every row; `collapsed` says whether the TUI folds it.
- `GET /v1/backlog` is the Backlog, loaded as the TUI loads it: the cached copy while it is younger than five minutes, else Jira, one load at a time; `?refresh=true` asks Jira anyway, as `g` does. It shows the Backlog as the user last left it (`hidden_boards` and `collapsed` from `board-state.json`, `merged` from its `backlog_merged`); the query `?merged=true|false` and `?hidden_boards=<name>` override it. Fields: `fetched_at`, `error` (Jira failed; the backlog is the last copy), `no_team_boards` (true when no space has a team board set, so the Backlog is empty by configuration and asks Jira nothing), `hidden_boards`, `merged`, `collapsed`, `boards` (`name`, `tickets`, `hidden`), `groups` (active sprints, then future sprints soonest first, one per sprint and board, or per sprint name while merged, then `Backlog` with the tickets in no sprint, folded unless `collapsed` lists `backlog:`: `group`, `title`, `board`, `dates`, `sprints` (ids), `count`, `collapsed`, `points` (`todo`, `doing`, `done`, `unestimated`; only when the site has story points), `rows`), `label_field`, `me`, `warnings`. It answers `502 backlog_failed` when Jira fails and there is no copy.
- `GET /v1/tickets/{key}/start?herdr=desktop|classic` is what the TUI's Start modal asks, from the code the TUI uses (`startChoices`, `agentChoices`): `herdr` (echoed), `opens` (Start opens an agent rather than going to a running one, so it asks which), `worktrees` (several worktrees to pick from: `repo`, `branch`, `path`, `agent` status when one runs there), `repos` (the space's repositories to pick from: `name`, `last_used`, `checked`), `agents` (the kinds installed that this Herdr can start), `last_agent`, `agents_error` (why none can be offered). Empty `worktrees` and `repos` mean Start asks neither.
- `POST /v1/tickets/{key}/start` runs the TUI's and `tkt herdr start`'s Start with the answers in its body: `{"herdr": "desktop"|"classic", "repos": [...], "worktree": "...", "agent": "...", "clone": true|false}`. `herdr` is required, since the detached daemon cannot tell which Herdr the user means when both run; `worktree` and `repos` exclude each other; `agent` must be one of the agent kinds the choices list, since the daemon runs it as a program. The daemon has no terminal, so a Start that would ask answers `409 needs_answer` with `"needs": "clone"|"worktree"|"repos"|"agent"` before opening anything, and the client asks the user and sends the request again with that answer (`clone: false` skips a repository with no clone). Opening agents waits for them to be ready, which can take minutes, so once every answer is in the daemon answers `202 {"id", "state": "started"}` and ends the Start with a `start.finished` or `start.failed` event (`{id, key, message}`) over the WebSocket; a Start that only focuses a running agent, as the TUI's "Go to the agent in Herdr" does, answers `200 {"id", "state": "finished"}`. A second Start of a ticket while one runs answers `409 start_running`; a Herdr that is not running `503 herdr_unavailable`; any other failure `422 start_failed`. Besides the token, it takes only `Content-Type: application/json` (`415` otherwise) and refuses an `Origin` other than the daemon's own (`403 forbidden_origin`), as the WebSocket does. Starting an agent writes nothing to Jira or GitHub, so it needs no UI confirmation.
- Move and Assign write to Jira, which changes the ticket for everyone, so a client asks the user to confirm in its own UI before calling `POST /v1/tickets/{key}/transitions` or `PUT /v1/tickets/{key}/assignee`, as the TUI does (a move's form, with its values on screen, is its confirmation); the daemon performs a valid request at once. Both take only JSON from no origin or the daemon's own, as Start does (`415`, `403 forbidden_origin`). After either, the daemon asks for a sync, as the TUI refreshes, so `/v1/board` and the WebSocket's events show the change; after an assignment the next `GET /v1/backlog` asks Jira, as the TUI reloads an open Backlog. A failing Jira call answers `404 not_found` when Jira does not know the ticket, `422 jira_rejected` with Jira's `messages` and `fields` (its message per field) when it refuses the values, and `502 jira_failed` otherwise.
- `GET /v1/tickets/{key}/transitions` is the TUI's Move menu, from the code it uses (`board.Moves`): `key`, `url` (the ticket in Jira, from the board) and `moves` in Jira's order, one per destination status: `id`, `to`, `in_jira` (its form needs fields only Jira's own form fills, so the client opens `url`; left out when the board has no `url`), and `fields`, the form the board fills before moving (`id`, `name`, `kind` `option` or `user`, `required`, `options` `{id, value}` for `option`); with no fields the move needs only the confirmation.
- `POST /v1/tickets/{key}/transitions` takes `{"id": "<move id>", "values": {"<field id>": "<option id or account id>"}, "comment": "..."}` and answers `200 {"key", "to"}`. It refuses, before writing anything, a move the menu does not offer now (`409 transition_unavailable`), one left to Jira (`409 needs_jira_form` with `url`), a field or option the form lacks (`400 bad_request`), and a required field left empty (`422 missing_field` with `field`, the message the TUI shows: "choose <name> first").
- `GET /v1/tickets/{key}/users?query=<text>` is the TUI's search of people to assign: `key`, `query`, `users` (`id` account id, `name`), at most 20, apps left out; under two letters it answers no users without asking Jira, as the TUI waits for them.
- `PUT /v1/tickets/{key}/assignee` takes `{"to": "me"}`, `{"to": "user", "account_id": "..."}` or `{"to": "nobody"}` and answers `200 {"key", "to", "account_id"}`.
- `GET /v1/tasks/agents?herdr=desktop|classic&ticket=<key>` (a ticket's feedback) or `&repo=<owner/name>&number=<n>` (a review of a pull request the board shows: a review request, someone else's or one of the user's) is the TUI's "Send … to" menus, from the code they use (`openAgents`, `agentChoices`): `herdr`, `phrase` (the task as the menu's title words it, such as `DEMO-1's feedback` or `the review of #820`), `agents` ("An open agent": `name`, `pane`, `status`, `folder`, `workspace`, `repo`, `branch`, `ticket`, `same_repo`; the free ones in a checkout of the task's repositories first, then the other free ones, then the busy ones, which queue it), `kinds` and `last_agent` ("A new agent"), `kinds_error`. A pull request the board does not show answers `404 not_found`, and before the first board `503 not_synced`.
- `POST /v1/tasks` runs the TUI's f and its "Send … to" and "Review with" menus: `{"herdr", "ticket": "<key>" | "review": {"repo", "number"}, "to": "own"|"open"|"new", "pane", "agent", "clone"}`. `own` sends a ticket's feedback (CI failures, review comments, unresolved threads, conflicts, collected from GitHub) to the agent in its worktree, as `tkt fix` does; `open` prompts the agent in `pane`, which must be an agent Herdr lists (a pane without one is refused, since the prompt would be typed into whatever runs there); `new` opens an agent where the work belongs, as the TUI's "A new agent" does, of kind `agent`, which must be one of `kinds` (`409 needs_answer` with `"needs": "agent"` when several are installed and none is named). A review's prompt comes from the board's copy of the pull request, never from the caller, and asks the agent to report its findings without posting to GitHub. A fix whose repository has no clone answers `409 needs_answer` with `"needs": "clone"`, `repo` and `into` (the first of `repo_roots`, where `gh repo clone` puts it) before cloning anything; the client asks, as the TUI's "Clone …?" does, and sends `clone: true`, or `clone: false` to give up. The clone's repository is the ticket's pull request's, never a path or URL from the caller. Opening an agent or cloning can take minutes, so once nothing more is asked the daemon answers `202 {"id", "state": "started"}` and ends with `task.finished` or `task.failed` (`{id, task, message}`, `task` being the ticket key or `owner/name#N`); a prompt to an agent already open answers `200 {"id", "state": "finished"}`. A second task for the same ticket or pull request while one runs answers `409 task_running`, a Herdr that is not running `503 herdr_unavailable`, any other failure `422 task_failed`. It takes JSON from no origin or the daemon's own, as Start does. Handing work to an agent writes nothing to Jira or GitHub, so it needs no UI confirmation; the TUI posts nothing to GitHub either (an agent's review findings stay with the user).
- `GET /v1/settings` is what the TUI's Settings shows from `config.toml`, as written (`~` unexpanded): `spaces` (`key`, `name`, `repos` `{repo, path}`, `inferred` (the repositories of the space's pull requests neither configured nor ignored, which Settings offers to pin or ignore; empty before the first board), `team_boards` `{id, name}`), `repo_roots`, `label_field`, `points_field`, and the choices that need no Jira: `columns` (`{id, title}` in order) and `marks` (`none` first). It shows nothing else of the configuration and never a secret (the token lives only in the credential store). What Settings lists from Jira has its own routes, asked when a section needs them, as the TUI asks: `GET /v1/settings/statuses?space=<key>` (`space`, `statuses`: `name`, `category`, `column`, `column_auto`, `mark`, `mark_auto`, as the Statuses section shows them), `GET /v1/settings/boards?space=<key>` (`space`, `boards` `{id, name}`, the space's scrum boards) and `GET /v1/settings/fields` (`fields`, the site's field names, for the ticket label and story points). A space that is not configured answers `400 bad_request`; Jira's errors answer as for Move: `404 not_found` when Jira does not know what was asked, `422 jira_rejected` when it refuses the request, and `502 jira_failed` otherwise.
- `PATCH /v1/settings` takes any of `repo_roots` (the whole list), `label_field`, `points_field` (empty: no label, or detect the points field) and `spaces` (`{"<key>": {...}}` with any of `repos` (the whole list of `{repo, path}`; a repository kept keeps its saved `base`), `ignore` (inferred repositories to ignore, added to `ignored`), `team_boards` (the whole list of board ids, in order; a board not saved yet must be one of the space's scrum boards) and `statuses` (`{"<status>": {"column", "mark"}}`, either or both, or `null` to bring it back to automatic; a column or mark equal to the automatic one is not saved)), and changes only those, with the checks and the save the TUI's Settings uses (`config.Save`: TOML, mode `0600`, replaced atomically), one change at a time. Text is trimmed as the TUI trims it. An unknown field, space, status, board, column or mark, a `null` anywhere but a status, an empty folder or repository, or a change the configuration's own checks refuse (such as a repository that is not `owner/name`) answers `400 bad_request` and writes nothing. It answers `200` with the new settings, sends `settings.updated` with them, and asks for a sync, which reads the new configuration, as the TUI's save refreshes the board. It writes nothing to Jira or GitHub, so it needs no UI confirmation. The folder browser (`ctrl+o`) and the form's completions from local folders and GitHub stay in the terminal. The daemon also sends `settings.updated` when another program, such as the TUI, changes `config.toml` (checked every two seconds); a TUI connected to the daemon shows the new settings, and a TUI save refuses to write over a `config.toml` changed since Settings read it, showing what the file now holds so the user makes the change again.
- Each `/v1/board` row also carries `card`, what the TUI's card says besides the ticket, from the same code (`board.CardOf`): `attention` (the reasons the ticket needs you), `points` ("3pt"), `who` ("Ada L.", or "unassigned"), `progress` ("1/3 subtasks · 1 to do") and `type_kind` (bug, epic, subtask, story, task or other, for its icon), `details` and `hint` (the preview's second line when the ticket is selected; the hint names "the agent" when one works on the ticket in the Herdr asked for, else "an agent"). The board also says `sync_label` ("✓ synced 3 min ago", "refreshing…", "! cached · 10:30"), as the TUI's status line words it.
- Agents per Herdr: Herdr 0.9.5 and Herdr desktop run agents of their own, so the daemon keeps each one's states apart (`agents_by`, `{"desktop": {...}, "classic": {...}}`, in the snapshot and in `agent.updated`) beside their most urgent union (`agents`, as before). `GET /v1/board?herdr=desktop|classic` shows only that Herdr's agents. The TUI shows only the agents of the Herdr whose terminal runs it, and none in a terminal of neither; the Herdr desktop mod asks for `desktop`.
- `tkt api METHOD PATH [--body JSON|-]` sends one request to the running daemon (starting it when none runs) with its token and prints `{"status": <code>, "body": <the answer>}`; it exits non-zero only when the daemon cannot be reached. The Herdr desktop mod uses it through `exec("tkt", …, {on: machine})`, since a daemon on another machine of the core (such as WSL) listens on that machine's `127.0.0.1`. Writes run in one step, as the API does: the UI client confirms with the person before it calls. The daemon logs every request to a mutating route (`write METHOD "PATH" → status`, the path quoted) in `daemon.log`.
- `POST /v1/herdr/agents` takes `{"agents": ["claude", …]}`, the installed agents Herdr desktop's `knownAgents()` lists (most picked first, at most 64; each a plain program name, else `400 bad_request`), and keeps them in `herdr-agents.json`; on Herdr desktop, agent kinds are then those of them installed, instead of the fixed list. The mod sends it once it knows which machine's tkt it uses. It looks for tkt with `tkt --version`, which starts no daemon, and asks the person which machine to use when tkt is on more than one.
- Not served: the ticket pane (Herdr 0.9.5's plugin pane; the mod shows details itself), a focus route (agent states are in `/v1/board`; focusing is Start and these tasks), and copying a task's prompt (the TUI does it only outside Herdr).
- `GET /v1/tickets/{key}` is also the details screen: beside `ticket` (with `prs` and `subtasks`), `description`, `acceptance_criteria`, `attachments`, `comments` and `warnings`, it adds `attention` (why the ticket needs the user, as the TUI's "needs you" line says it, such as `CI failing`), `agent` (its agent's state from the board, when one runs) and `work` (its branches and worktrees: `key`, `repo`, `branch`, `path`, `source`, `linked_at`; left out when they cannot be listed). Each is left out when empty.
- `GET /v1/tickets/{key}/context` answers `{"key", "text"}`, `text` being the Markdown the TUI's "copy context" (`c`) puts on the clipboard, built by the same code (`renderContext`, without downloading images); the client copies it itself. A failing Jira answers `502 detail_failed`, as the detail does.
- `GET /v1/board/state` is what the TUI remembers in `board-state.json`, each field as it takes effect: `view` (`columns` or `list`), `team`, `hidden_boards`, `hidden_repos`, `collapsed`, `team_prs` (following `team` while never set), `backlog_merged`. `PATCH /v1/board/state` takes any of those fields and changes only them, writing the file the TUI writes, in its format (lists sorted, without repeats, left out when empty; mode `0600`, replaced atomically), one change at a time; it answers `200` with the new state and sends `state.updated` with it. An unknown field, a `view` other than `columns` or `list`, a non-boolean or `null` flag, or a list that is not of non-empty names answers `400 bad_request` and writes nothing. It writes nothing to Jira or GitHub, so it needs no UI confirmation. The daemon also sends `state.updated` when another program, such as the TUI, changes the file (it checks every two seconds), and a TUI connected to the daemon takes the new filters; a TUI's save keeps what changed elsewhere since it last read the file, field by field, and a filter list keeps both sides' additions and removals.

## 4. Configuration and data

- Configuration: `~/.config/tkt/` (`$XDG_CONFIG_HOME/tkt` when set). Nothing about a specific organization is hard-coded; everything comes from configuration or is discovered from Jira. Format and exact fields are decided at the start of phase 1.
- Configured, because Jira cannot know it: Jira base URL and account, each project's repositories (`owner/name`, optional) and their local paths, the `gh` account per GitHub organization, optional acceptance-criteria field, and status overrides.
- Local clones are found, not typed: `start`, discovery, and Herdr work on the local checkout, so `tkt` resolves each `owner/name` to a folder by (1) an explicit `path` in that repository's configuration, else (2) scanning the configured root folders (`repo_roots`, for example `~/dev/work`) for git repositories whose remote matches, cached until it stops matching, else (3) offering to clone it into the first root with `gh repo clone`.
- Discovered from Jira, never configured: statuses per project (`/project/{key}/statuses`) and transitions, fetched at runtime per issue (`/issue/{key}/transitions`) because they depend on each issue's workflow.
- Board columns default to Jira's `statusCategory` (To Do, In Progress, Done); configuration overrides only what categories cannot express, such as which status means "in review".
- `tkt init` asks for the Jira URL, reads the user's projects and statuses, and writes a draft configuration; the user only fills in repositories. For each space it lists the columns its statuses land in ("In Progress  En curso, Pending test") and asks which to move ("Pending test=In Review", by status name or its start, column by title or configuration name), saving them in `status_overrides`; an empty answer keeps them.
- A Jira project can span many repositories, one per product. Reference test case: site `https://example.atlassian.net`, project `DEMO` (Example Product), whose product Web lives in `example-org/web`; sample ticket `DEMO-170450`.
- Data: its own directory with mode `0700` — `$XDG_DATA_HOME/tkt` (default `~/.local/share/tkt`) on Linux and WSL, `~/Library/Application Support/tkt` on macOS. Holds the SQLite cache, the daemon token, and logs.
- Secrets are never stored in configuration or data files (see section 7).

## 5. Conventions

- The ticket key is part of the branch name (for example `feature/DEMO-123-slug`). This joins Jira and GitHub without manual mappings: a PR belongs to a ticket when its head branch contains the key.
- `tkt` never runs the git commands that create branches or worktrees. The agent creates them, following each project's own rules for branch names (fix, feature, docs, ...), base branches, and tooling (plain git, git flow, project scripts). `tkt` enforces one invariant: the branch name must contain the ticket key, in any case (`feature/DEMO-123-x` and `test/acto-123-x` both work); only keys of configured spaces count, so words like `fix-123` never match.
- `tkt start <KEY>` lets the user pick the repositories (interactive, preselected with the last set used for that space; `--repo` skips the prompt; with several worktrees, `--worktree PATH` picks one, and `tkt herdr start` goes straight to the one an agent works in). From the board, Start asks these questions first in a modal that works with keyboard and mouse ("Which repositories?" with the last used checked, space or a click toggles; "Which worktree?" with each worktree's agent, enter or a click opens; then, when Start opens an agent rather than going to one already running and several are installed, "Which agent?" with the last one chosen preselected, passed on as `--agent`), then runs Start with the answers on a cleared screen; the modal is the same in the full window and the tray panel, only narrower. With `label_field` set under `[jira]` (a field name such as "Product", resolved to the site's field id; set it in Settings → Board → Ticket label, where Tab completes from the site's fields), the selected ticket's detail line starts with that field's value as a badge and every detailed card gets a line for it above the type and assignee, the value shown as a badge (blank on a ticket without a value, so cards keep one height; compact cards leave it out); a missing field becomes a warning and an empty one shows nothing. The selected ticket's title line shows its Jira status beside the key, on its column's color (To Do gray, In Progress blue, In Review mauve, Done green) and with its mark's icon (`DEMO-1  ◇ Pending test  · Filter accounts`); its actions menu names the status too, under its title ("Actions for DEMO-1" over "Pending test"). Story points come from the field `points_field` under `[jira]` names (Settings → Board → Story points, Tab completing from the site's fields), or, unset, from a field called "Story Points" (company-managed spaces) or else "Story point estimate" (team-managed), added to the sprint searches the sync already makes, so they cost no request of their own. They show beside a card's key ("ACTO-170450 3pt", giving way when the flags need the room), in each column's title ("In Progress  3 · 8 pts"), in an SP column of the list (dropped after ASSIGNEE on narrow panes), and first on the selected ticket's detail line ("3 points · Pedro P."); an unestimated ticket shows none. Menus stay narrow: their actions' labels set the width (at least 46 columns), the title is cut past 44, and the details go on dimmed lines under the title, wrapped at their " · " instead of widening the box, as does the key footer; a pull request's menu reads "Pull request #820" over "example-org/web · alex · review requested" for someone else's and "Pull request #815" over "DEMO-4 · In Review" for the user's, opening it with "Open in GitHub ↗". The key legend lists only the keys that act on the screen in view: no density or view outside the columns and the list that can switch, "↑ to reviews" and "review menu" only while the review strip shows, "fold group" in the PRs filter, and repos only when there are repositories. The board's sync state (`✓ synced 3 min ago`, a spinner while refreshing, `! cached · 15:04` when the last refresh failed) sits at the bottom right, on the key legend's last line, so the header keeps its room for the title and controls. and opens an agent in each repository's main checkout with an initial prompt: work on the ticket, create the branch and worktree per project rules, save the context with `tkt context`, and register with `tkt link`. In phase 2 the agent creates the worktree through `herdr worktree create`, so Herdr sees the new workspace.
- Agents: tkt keeps no list of agents. The kinds come from Herdr, which lists the agents it can start only in `herdr agent start --help` (`--kind`'s "[possible values: …]", each named after its executable), and tkt keeps those whose executable is in `PATH` (`tkt doctor` names them). Start opens the only one installed, else asks which ("Open which agent?", the last one chosen preselected and remembered as `last_agent` in `state.json`), or takes `--agent KIND`; the board learns the installed agents as it opens and asks the same question in its modal and in "A new agent ▸". There is no fallback agent: without Herdr in `PATH` ("cannot tell which agents are installed: tkt learns them from Herdr (`herdr agent start --help`), which is not in PATH"), with a help listing none ("cannot tell which agents Herdr can start: `herdr agent start --help` lists none; update Herdr"), or with none of its kinds installed ("no agent Herdr can start is installed; install one of: …"), nothing opens and that message says why. Inside Herdr the agent starts with `agent.start` and gets its prompt with `agent.prompt`, the same for every kind, which waits up to 5 s for the agent to start working or ask a question; when it does neither, the text was left unsent (a slow terminal still reading a long paste when Herdr pressed Enter), so tkt presses Enter once more with `pane.send_keys`; agents take a first prompt on their command line each in their own way, so outside Herdr `tkt start` opens the agent with no arguments and puts its prompt on the clipboard (and prints it) to paste.
- `tkt link [KEY]`, run from the worktree, registers the branch and path (the key is inferred from the branch when omitted), and the UI updates immediately. It rejects a branch without the key and explains how to fix it. In phase 4 the same operation is an MCP tool.
- `tkt unlink [KEY]` forgets a link: the current worktree's branch (or `--dir`'s), or with KEY every link of that ticket, and clears the `tkt_key` mark from every agent pane marked with a ticket it unlinked ("✓ KEY ✗ agent NAME (PANE)"), since that mark alone keeps an agent on its ticket; it says "nothing is linked to branch …" or "no work is linked to KEY" when there was neither a link nor a marked agent. A branch git still has keeps showing through discovery. Links also go stale on their own: when a link's worktree no longer exists in a repository tkt scanned, it is left out once git no longer has its branch either, and keeps only its branch while git does; `links.json` itself is changed only by `link` and `unlink`.
- Discovery keeps the board correct when nobody calls `tkt link`: `tkt` scans `git worktree list` and the local and remote branches of configured repositories, and associates every branch that contains a ticket key. Linking gives immediacy; discovery gives correctness.
- Repositories are configured as `owner/name` and may belong to any GitHub organization; nothing is tied to a specific organization.
- A ticket can span several repositories (for example, one user story with backend and frontend work). A Jira space (project) maps to a list of repositories; `tkt start` opens one agent per selected repository, and each creates its own branch and worktree.
- A ticket aggregates the pull requests and checks of every repository whose branches carry its key. Its board status is the most urgent one among them (for example, failing CI in any repository marks the ticket).
- `tkt context <KEY>` prints the ticket as Markdown: title, description (ADF converted to Markdown), acceptance criteria, attachments, and the latest comments. `--images <dir>` downloads image attachments so the agent can see them; other attachments are linked. The agent saves it as `.ticket.md` in the worktree (gitignored); both the Herdr `ticket` pane and the agent read it.
- `tkt start` on a ticket that already has a linked or discovered worktree opens the agent there instead of asking it to create a new one.
- Commands print human-readable output by default and offer `--json` with a stable schema for Herdr, the UI, and agents.
- In phase 1, `tkt start` only suggests the Jira transition to "In Progress"; executing it is a write and arrives later with UI confirmation.
- Usually one ticket is active, but several can be active at once; nothing assumes a single active ticket.

### Board scope

- Tickets assigned to the user in open sprints across configured projects, plus finished tickets the user once held and worked (teams often reassign a ticket to QA or a reviewer when it is done): ones whose status the user changed (`status CHANGED BY currentUser()`), or, held but never moved, ones with a pull request the user's gh account opened (from the listing, so one with only old merged pull requests is missed); one only held a moment shows with the team's tickets instead, plus pull requests where the user's review is requested.
- Each space has its own sprint; the Sprint tab's context line shows the active sprints the user's tickets belong to (for example `DEMO S42 · 4d left`), read from the tickets' own Sprint field. Listing every board of a space shows other teams' sprints and costs one request per board, so it is avoided.
- `reviews` in the configuration selects review requests: `direct` (default; requests addressed to the user in configured repositories), `team` (also requests to the user's teams, which include CODEOWNERS and dependabot traffic), or `off`.
- Review requests on pull requests opened by bots (GitHub reports the author as a `Bot`, e.g. dependabot or Aikido autofix) are hidden: `tkt list` never shows them, and the board's PRs filter shows them with `b` or a click on its "show bots" line. The board lists review requests grouped by repository.
- A ticket whose status names it blocked ("Blocked", "Bloqueado") sits in To Do with a `⊘` mark, unless the space maps that status to another column or another mark.
- Each status of a space has a column and a mark. Its column comes from `status_overrides` (`"Pending test" = "review"`) or the automatic rule: a blocked name waits in To Do, Jira's "done" category goes to Done, an "indeterminate" status whose name says review ("review", "revisi") to In Review, any other "indeterminate" one to In Progress, the rest to To Do. Its mark is an icon shown with the status name on the card's first line, before the agent's dot ("◷ On hold"), and before the key in the list; it shrinks to the icon when the name does not fit or another flag is there. It comes from `status_marks` (`none`, `diamond` ◇ blue, `blocked` ⊘ orange, `clock` ◷ teal, `flag` ⚑ mauve, `star` ★ yellow, `triangle` ▲ green; no red, which belongs to an agent that needs the user) or by default: `blocked` for a blocked name, `diamond` when `status_overrides` moved the status out of its automatic column, otherwise none.
- Settings has a Statuses section listing, per space, every Jira status (`/project/{key}/statuses`, asked once when the section opens) with its column and mark, each followed by "· auto" while it follows the automatic rule: `enter` moves the status to the next column and `m` gives it the next icon (none after the last), `d` brings both back to automatic; only what differs from automatic is saved, in `status_overrides` and `status_marks`. It fits the tray panel like the other sections.
- Subtasks: a parent's card shows its progress first ("3/4 subtasks · 1 to do", the last part when a subtask has not started though its parent has); each subtask also gets a card in its own column, done ones included as on Jira's board, "↳ KEY" and "of PARENT", right after its parent when they share a column. The list shows every subtask indented under its parent ("↳ KEY", done ones dimmed), each with its own actions. Epics are not shown.
- A ticket in progress whose status names a review ("Code Review", "In Review", "En revisión") sits in In Review, unless the space maps that status to another column; Jira files such statuses as in progress.
- Repositories are optional configuration: `tkt` infers each space's repositories from the pull requests Jira links to the user's tickets (development panel) and from the PRs matched to them, and uses that set for CI, review requests and the GitHub account; configured repositories add to it and set local paths. The `gh` account for an owner is the configured one, else the logged-in account named like the owner or belonging to the organization (`GET /user/memberships/orgs/{org}`), remembered in the data directory.
- "Needs you" means: one of my tickets has failing CI or requested changes. PRs awaiting my review are listed apart, under "Review requested". `tkt list --needs-you` and the daemon's `needs_you` keep this meaning; the board shows it inside its PRs filter.
- Subtasks are grouped under their parent story.
- CI status comes from GitHub Actions checks.

## 6. Integrations

Jira — base URL, authentication method, projects, statuses, and transitions are asked before phase 1 code.

Jira — Jira Cloud REST API with email + API token stored in the keychain. "My sprint" is `assignee = currentUser() AND sprint in openSprints()` across configured projects (every project uses sprints). `.ticket.md` always includes the full description; a project may declare an optional acceptance-criteria custom field, rendered as its own section, because where criteria live varies by project and author. The latest 5 comments are included (configurable).

GitHub — direct REST/GraphQL API (one GraphQL query fetches PRs and checks for many repositories; testable with `httptest`; no subprocess per call). The token comes from the user's `gh` login via `gh auth token --user <account>`, with the account configured per organization, so the active `gh` account does not matter. When `gh` is unavailable, `tkt` asks for a fine-grained PAT and stores it in the keychain. Tokens are held in memory only.

### Herdr plugin (phase 2)

Based on https://herdr.dev/docs/plugins/ and https://herdr.dev/docs/socket-api/.

- Which Herdr: tkt speaks to Herdr 0.9.5 (its socket) and to Herdr desktop (herdr-core through `hc`, the window through `herdr-app`). A command run in a terminal uses the Herdr it runs in: `HC_TERMINAL_ID`, `HC_TERMINAL_SOCKET` or `HC_SCOPE` mean Herdr desktop (preferred when both sets are present), `HERDR_ENV` or `HERDR_SOCKET_PATH` mean Herdr 0.9.5. Otherwise tkt uses the one running (Herdr 0.9.5 when its socket accepts a connection, Herdr desktop when `hc server status` exits 0); with both running it does not guess and fails with "both Herdr and Herdr desktop are running: run tkt from a terminal inside the one to use"; with neither it keeps Herdr 0.9.5 and its "herdr is not running" error. `tkt doctor` adds the choice, or that refusal, to its `herdr` line. Board behavior that needs a Herdr (Start through `tkt herdr start`, agent states, sidebar tokens) also works in a Herdr desktop terminal; the plugin-pane parts (ticket pane, Fix stepping aside) stay Herdr 0.9.5 only.
- On Herdr desktop: an agent starts in a terminal of its own beside the pane tkt gives it (hc cannot start a program in a live terminal), so tkt marks, focuses, prompts and records the agent's terminal and closes a split it opened only for the agent. Spaces, splits and closing go through hc, which works on every machine of the core, so tkt runs the same on the computer that shows the window and on another machine of its core reached over SSH (such as WSL), where `herdr-app` cannot reach the window: a space is opened by starting its first terminal with `hc run --bg --json --no-parent --cwd <folder> --label herdr.space=<new id> --label herdr.tab=<new id> [-- <program>]` (an id the window does not know makes it open a space or tab; a shell when no program is given), a split by starting a shell with the pane's `herdr.space`/`herdr.tab` labels, and a pane or space is closed by ending and removing its terminals (`hc kill`, `hc rm`), which closes the pane and, with the last one, the space. `herdr-app do` runs only for what exists only in the window (select a space, focus a pane, name a space with `space.rename`, close what is left of a space), and only once `herdr-app status` answers (kept 30 s); where it does not, tkt skips them and prints once "tkt cannot reach the Herdr desktop window from this machine, so it opens spaces there without focusing or naming them", and the flow goes on. tkt starts terminals through the API's `terminal.run` rather than `hc run`, since herdr-core starts them with its own environment, whose PATH may lack hc and the agents (on WSL, Homebrew's and `~/.local/bin`): each gets tkt's `PATH`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `HERDR_APP_HOME` and `TKT_*` variables (never one whose name holds TOKEN, SECRET or PASSWORD) over the core's, so an agent's own `tkt` and the closer use the config and data of the tkt that started them. Prompts go through the API's `terminal.send` without a caller, so they arrive as typed rather than wrapped as `<hc from="t3">` reports. Closing a pane or a space also removes its finished terminals from hc (`hc rm`), and finished terminals are never listed as panes or agents. The focused pane comes from `herdr-app status`. A space matches a worktree by its folder, since Herdr desktop has no worktrees. The agents tkt offers are Herdr 0.9.5's kinds installed in PATH (Herdr desktop's own list reaches only mods). Herdr desktop cannot notify outside mods, so tkt prints those messages; with the window closed or out of reach, window actions fail with "herdr desktop window is not open: open Herdr", and focusing an agent only warns.

- A plugin is a directory with a `herdr-plugin.toml` manifest; the whole Herdr CLI is the plugin API. The plugin stays thin: it calls `tkt` and calls Herdr back through `HERDR_BIN_PATH` (portable across Unix sockets and Windows named pipes).
- Action `start`: a ticket without a worktree always gets one, so the repository's main checkout stays free. An agent cannot change its own folder or workspace, so Start runs two: a setup agent, the chosen kind, opened in a split tkt creates for it with its folder at the repository (beside a pane open at the repository, else beside the pane Start runs in, else in a workspace tkt opens next to the repository; never a workspace at the repository, which Herdr makes the head of the worktree's group and refuses to close alone), whose only prompt is to pick the branch and its base per the repository's rules, create the worktree with `herdr worktree create` (`worktree.create` creates the branch and returns the new workspace and root pane) and stop. Before prompting it, tkt saves a handoff in `state.json` (ticket, repository, the setup agent's pane, name and kind, the workspace when tkt opened one for it, the time). When the `worktree.created` hook below sees the handoff's ticket and repository, it starts the same kind in the new workspace's root pane (the event names the workspace, not its pane, so tkt finds the one empty pane there), prompts it to save the context, copy from the main checkout the ignored files the project needs to run (such as `.env.local`) when the project's rules call for it, confirm the link and implement, focuses it, and closes the setup agent's pane, then the workspace tkt opened for it once only the pane it opened with is left. A question the new agent shows first, such as Claude Code's trust prompt in a folder it never saw (`agent_blocked`), is waited on for up to four minutes before the prompt; Claude Code trusts a folder whose parent it trusts, so trusting `~/.herdr/worktrees` once spares that question for every worktree. On any failure the setup agent stays and Herdr shows a notification; a handoff older than an hour is dropped. `agent.start` gets two minutes to see the agent ready (Herdr's default is 30 s, which a cold start on a busy machine outlasts), and a split Herdr still calls busy because its shell is starting is retried for up to ten seconds; when the setup agent does not start, Herdr shows a notification (the board's status line is easy to miss) and tkt closes the split it opened unless an agent came up there anyway. A ticket that already has a worktree opens its agent there, reusing an open workspace at it with no agent (a split next to a busy pane), else a new one.
- Start on Herdr desktop: it has neither `herdr worktree create` nor the `worktree.created` hook, so the setup agent's prompt asks it to create the worktree with git where the repository's rules put worktrees (else Herdr desktop's own `~/.herdr/worktrees/<repository folder>/<branch with / as ->`) and then run `tkt link KEY` from inside it. `tkt link`, run in a Herdr desktop terminal (`HC_*` set), takes the pending handoff for its ticket and repository and opens one space at the worktree whose first terminal runs the same kind, with the same handoff prompt as its first message (`hc run … -- <kind> <prompt>` for Claude Code and Codex, which take it as an argument; any other kind is prompted once ready, never while it shows no status), named `KEY · <worktree folder>` where the window can be reached, and marks and focuses the agent's terminal. The setup agent runs that `tkt link`, and closing a terminal ends every process started in it, so herdr-core runs the closer (`terminal.run` with `rm` and no parent, of `sh -c` around `tkt herdr close-setup …`; the shell logs "close-setup started" to `handoff.log` in the data dir before it runs tkt, which logs each step there): it ends and removes the setup agent's terminal only, then selects the new space and focuses its agent again. - Limitations to design around: tokens do not survive Herdr restarts; values are limited to 80 characters (per the project brief); plugins have no daemons — `[[startup]]` hooks are one-shot and must restore state and exit; plugins ship no default keybindings (users bind actions in their own config).

## 7. Security

- Daemon: `127.0.0.1` only, 256-bit token in a `0600` file, `Origin` check plus `hello` token on WebSocket (section 3).
- Jira and GitHub tokens live in the OS credential store, behind one secrets interface with a backend per platform: macOS Keychain; Linux Secret Service; on WSL, Windows Credential Manager reached through `powershell.exe` (read once at startup and held in memory, since PowerShell takes about a second to start). No encrypted-file backend: with the key already in Credential Manager, a second encrypted copy adds a moving part and no security. `TKT_JIRA_TOKEN` works everywhere as a documented, less secure fallback for tests and headless use. Never in plain text in the repository, configuration, logs, or chat.
- Writes (Jira transitions, comments, merges) require confirmation in the UI, never inside the agent. The MCP server pauses, emits `confirmation.requested` over WebSocket, and executes only after the user accepts in the UI.
- During development, only read operations run against real Jira and GitHub. Any write against real services requires explicit approval first.

## 8. LLM integration (phase 6, optional)

- The core is deterministic and does not use an LLM.
- One-shot tasks (ticket summary, PR description): `claude -p --output-format json --json-schema <schema>`, with or without `--bare` per the constraint below.
- Panel chat: the daemon supervises one persistent Claude Code process with `--input-format stream-json --output-format stream-json`, restarts it with exponential backoff, and forwards events to the UI. Isolated configuration: `--bare`, only the `tkt` MCP server, restricted tools (no shell).
- Claude Code in workspaces reaches `tkt` first through a skill that uses the CLI, then through MCP with typed tools.
- Every AI feature is optional by configuration; when it fails, `tkt` keeps working.
- `--bare` constraint (verified with `claude --help`): it skips hooks, plugins, auto-memory, keychain reads, and `CLAUDE.md` auto-discovery, and authenticates only with `ANTHROPIC_API_KEY` or `apiKeyHelper` via `--settings`, never OAuth. A subscription (OAuth) user needs an API key for every `--bare` call; otherwise isolate with explicit flags instead. Decide per feature in phase 6.

## 9. Platforms and tray app (phase 5)

- Web first: the daemon serves the React UI (embedded with `go:embed`) on localhost, which works on every OS including WSL.
- Tray app wraps the same UI. Shell is interchangeable: Wails v3 or Tauri; evaluate Wails v3 maturity when phase 5 starts.
- Two surfaces, always designed together: the full window (browser or app window) and the tray panel (about 400×720). Every screen and state exists in both.
- The tray panel opens from the menu bar or system tray icon (labelled `tkt`, default on), the global shortcut, or an optional floating `tkt` button that the user can drag to any screen edge (off by default). It expands into the app window instead of opening the browser; the only exception is external links to Jira and GitHub, always marked with ↗.
- Settings (in both surfaces) write the same `config.toml` the CLI reads: accounts, spaces and repositories, panel and shortcut, sync and notifications, AI, advanced.
- Onboarding: on first run, or when a token expires, the UI asks for the Jira site and email, opens Atlassian's API-token page, validates the pasted token against Jira, and stores it in the platform's credential store without asking where. GitHub needs no step when `gh` is logged in. `tkt init` offers the same flow in the terminal. Expired or failing credentials never break the board: it keeps showing cached data, marked as stale, with a one-click renew.
- WSL: the daemon runs inside WSL next to the repositories; the tray app runs on Windows. They talk over HTTP on localhost (WSL2 forwards `localhost` to Windows by default); the tray app's origin joins the WebSocket `Origin` allowlist. No Unix sockets across the boundary.
- Inside WSL live everything else: CLI, daemon, `git`, `gh` (logged in inside WSL), `claude`, and Herdr. Herdr runs inside WSL, so the plugin targets `linux` and calls `tkt` directly.
- The tray app checks `GET /health` and starts the daemon if it does not answer. It captures the user's login-shell `PATH` first: apps launched from Finder get a minimal `PATH`, and the daemon needs `git`, `herdr`, and `claude`.
- Single-instance app with `--toggle`, for Wayland, where apps cannot register global shortcuts.

### Installation

One command installs `tkt`; the onboarding offers everything else.

| When | How |
|---|---|
| Phase 1 (single user) | `go install github.com/pavp/tkt/cmd/tkt@latest` (public repository) |
| Releases | GitHub Releases built with GoReleaser (macOS and Linux, arm64 and amd64) on every `v*` tag, and the Homebrew formula in `pavp/homebrew-tap`: `brew install pavp/tap/tkt`, which also covers WSL through Linuxbrew |
| First run | `tkt init` in the terminal, or the onboarding in the UI (same steps) |
| Daemon (phase 3) | `tkt daemon install` registers a launchd agent (macOS) or a systemd user service (Linux; on WSL systemd must be enabled in `wsl.conf`) so the daemon starts at login; the tray app also starts it when `GET /health` does not answer |
| Herdr plugin (phase 2) | `tkt herdr install` links the plugin shipped inside `tkt` |
| Claude Code (phase 4) | `tkt claude install` adds the skill and registers the MCP server (`claude mcp add tkt -- tkt mcp`) |
| Tray app (phase 5) | `.dmg` on macOS (signed and notarized, or Gatekeeper warns), an installer on Windows, AppImage on Linux |

- The onboarding ends with an **Integrations** step: it detects Herdr and Claude Code and offers to install the plugin and the MCP server, one click each. Each `install` command has a matching `uninstall`.
- `tkt doctor` checks the whole chain: binary version, configuration, credentials, `gh`, `git`, the agents installed, Herdr plugin, daemon service.
- Installers, the release pipeline, and service registration change the user's environment and are hard to undo, so each lands in its own reviewed commit.

## 10. Technical notes

- Reading line-delimited JSON in Go: `bufio.Scanner` caps lines at 64 KB. Enlarge its buffer (`Scanner.Buffer`) or use `bufio.Reader`. Applies to stream-json from Claude Code and to any JSONL protocol.
